Paso 1

Crear el repositorio

Lo hace una sola persona

  • New repository en GitHub.
  • Nombre: pln-marketing-apellidos, sin espacios ni acentos.
  • Visibilidad: privado.
  • Marcad Add a README file.

Y después, colaboradores

  • Settings → Collaborators → Add people.
  • El otro miembro del equipo, con permiso de escritura.
  • La profesora, con permiso de escritura.
  • La invitación hay que aceptarla: hasta entonces no se puede tocar nada.

Quien no tenga cuenta de GitHub, que la cree ahora con el correo de la universidad, que es el que da acceso al paquete de estudiante.

Paso 2

La estructura del repositorio

Las tres capas de datos son las mismas que vimos ayer en el modelo de infraestructura, más una carpeta de muestra que sí se versiona.

data/raw

Capa bruta: los datos tal como llegan. No se sube al repositorio.

data/sample

Muestra pequeña y anonimizada. Sí se sube, para que el proyecto se pueda reproducir.

data/clean

Capa limpia: sin duplicados, formatos estandarizados. No se sube.

data/analytic

Capa analítica: agregados y resultados. No se sube.

docs

bitacora.md: el registro de decisiones. De aquí sale la memoria final.

Los datos crudos quedan fuera por tamaño y porque pueden contener datos personales, incluso en un repositorio privado.

Paso 4

El ciclo que repetiréis todo el curso

Rama
se trabaja fuera de la principal
→
Cambio
se edita y se confirma
→
Pull request
se propone integrar
→
Revisión
la hace el otro miembro
→
Integración
entra en la rama principal

Hoy lo hacéis una vez entera, con la primera entrada de la bitácora: lo hace el miembro que no creó el repositorio y revisa el otro.

Por qué así y no subiendo cambios directamente: el historial de commits documenta el trabajo de cada uno, y la revisión obliga a que ambos conozcan todo el proyecto. En la defensa final se pregunta a cualquiera de los dos por cualquier parte.

Paso 5

El entorno: GitHub Codespaces

El proyecto se desarrolla en el repositorio, así que el entorno también. Codespaces abre un entorno completo en el navegador, sin instalar nada en vuestro equipo.

  1. En el repositorio, botón verde Code → pestaña Codespaces → Create codespace on main.
  2. Cuando abra, en la terminal: pip install -r requirements.txt.
  3. Abrid y ejecutad notebooks/00_comprobacion_entorno.ipynb.
  4. Los cambios se confirman desde la pestaña de control de versiones, sin salir del navegador.

El notebook debe terminar con "Entorno correcto". Si alguna librería sale como FALTA, el propio notebook indica el comando para instalarla.

Norma

Las claves no se suben nunca al repositorio

Un token es una contraseña. Una vez subido queda en el historial de git aunque se borre en el commit siguiente, y cualquiera con acceso al repositorio puede recuperarlo.

Cómo se hace bien

  • Las claves van en un fichero .env.
  • .gitignore excluye .env: ya viene configurado en la plantilla.
  • Se copia .env.example a .env y se rellena.

Si se sube una por error

  • Dadla por comprometida.
  • Revocadla en la plataforma que la emitió y generad otra.
  • Borrarla del repositorio no basta.

Antes de salir

Lista de comprobación

  1. El repositorio existe y es privado.
  2. Los dos miembros y la profesora tenéis acceso, y las invitaciones están aceptadas.
  3. La estructura de carpetas está subida.
  4. El README.md tiene, al menos, equipo, problema y sistema.
  5. Hay una pull request creada, revisada y fusionada.
  6. El notebook de comprobación se ejecuta sin errores.
  7. En el historial aparecen commits de las dos personas.
